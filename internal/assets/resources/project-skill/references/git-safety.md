# 代码提交与推送操作

身份和消息只按 [git-conventions.md](git-conventions.md)；测试与验收只按 [verification.md](verification.md)；整合和清理只按 [closure.md](closure.md)。本文件维护提交授权、操作一致性与推送范围，不另外设置交付验收。

遇到不支持、未知、失败或检查覆盖不足时，必须按 [git-fallback.md](git-fallback.md) 补齐操作所需证据。doctor、远端合并记录和单个脚本成功都不是推送许可；核验不清则暂停对应代码动作。

## 提交前后

1. 明确仓库、分支、HEAD、实际目标、待执行操作及单写入者。只暂存本次逻辑变化，查未解决冲突、暂存/未暂存/未跟踪内容；不盲目 add 全部或 commit -a，不夹带凭据、其他活动或机器文件。
2. 一次提交覆盖一个可解释的逻辑变化，其代码、对应测试和必要说明一起保存；彼此独立的 CI、算法或机械移动拆开。Task 不决定提交次数。尚未完成或未通过本次适用检查的保存点使用 WIP，明确实际状态；不能据此通过 Topic review/ready。
3. 准备准确暂存 diff、暂存树、预期父提交、最终消息文件及有效身份；验证证据引用已有活动报告，并报告未测范围。消息文件放工作树外，使用文件参数传递，避免 shell 插值。本人创作提交先通过 commit_check preflight；保留原作者的重放/外部 amend 按下表对照原始对象，不套用双重身份必须相同的模式。
4. 展示准确 diff/完整文件链接、完整消息、身份、验证结果和拟执行动作，等待用户对本次具体结果批准。开发授权、验收或此前提交批准不替代；明确展示的多条结果可以一次批准，不包括未来未知提交。
5. 批准只覆盖所示暂存树、父提交/基线、目标、消息、身份和操作。提交前重新核对这些对象及与执行有关的 hook/签名设置。任一改变或出现冲突处理，先更新材料并重新 review。无需生成 review.json、摘要文件或审计目录。没有变化且原批准仍适用的失败重试，不重新索取同一许可。
6. 使用已审核 index 和消息创建批准的提交，保留消息原文（普通提交使用 `git commit --cleanup=verbatim --file <文件>`）；不临时暂存、不额外加 trailer、不绕过 hook/签名。提交后，本人创作提交运行 postcheck；保留原作者的操作直接读取实际提交，对照原 author、本人 committer 和已审核消息。两者都由 agent 比对实际 tree、parents 与批准对象，并确认当前分支/HEAD 仍指向预期结果。若不一致，停止后续推送、如实报告，不静默 amend。

未跟踪文件列表不代表文件内容快照。未跟踪内容只有被暂存后才属于本次提交；已有未跟踪文件内容改变，若影响已报告的构建/测试输入或提交范围，相应验证/批准失效。未纳入提交的代码、配置不能偷偷充当“提交自身可通过”的证据。验证记录须注明暂存内容与实际测试工作树的差异，以及外部夹具/工具输入；无法确认输入是否变化就重跑受影响检查。无关笔记变化不触发整个项目重审。检查脚本不承诺冻结工作区。

## 各操作的确定性核对

所有产生新 commit 的方式都遵守上面的准确结果审批。amend、cherry-pick、rebase 仅在用户明确要求该操作和范围时执行；保留原 tip 的可达恢复引用，不把“允许开发”解释为允许改写历史。

| 操作 | 创建前必须明确 | 创建后必须一致 |
|---|---|---|
| 普通提交、squash | 实际执行提交分支的当前 HEAD 为父提交（普通开发在 Topic 分支，整合在目标分支，首次提交无父）；最终暂存树和完整消息 | parents、tree、消息、本人双重身份 |
| merge commit | 目标 HEAD 与被整合 tip；冲突已处理的最终树与消息 | 父提交顺序为目标后源、最终树、消息、本人双重身份；快进不创建 commit |
| amend | 被替换 SHA、其原 parents、最终树与完整新消息、原 author | parents 保持、tree/消息按批准；本人原提交用本人双重身份，外部原提交保留原 author，新 committer 为本人 |
| cherry-pick | 原 SHA 与原 author、实际目标父提交、应用后的最终树/消息；原提交为 merge 时先明确选定主父语义 | 新父为实际目标、结果树/消息匹配，原 author 保留，新 committer 为本人 |
| rebase | 原 tip/目标基线、按顺序的原提交列表、每条原 author、保留/丢弃/合并决定 | 每条新提交父关系与选定拓扑、已批准树/消息、原 author/本人 committer，最后核对完整映射和无意外丢失 |

cherry-pick 可以先用不创建提交的方式准备暂存结果，冲突解决后才进入批准；不让“一次同意操作名”替代结果审核。rebase 必须逐条准备实际重放结果后审批、创建并核对，新一条以已核对结果为父；不能让自动批处理先生成未审核提交。存在 merge 拓扑时还须展示各父对应关系，不能静默线性化。当前工具/环境无法提供这些逐条检查时，明确停止该重写操作并说明缺失条件；不使用模糊的“人工同等检查”放行。这不是要求为普通提交安装重写引擎。

既有外部提交只是被 merge 保留时不重审其作者为本人，也不重写其消息。外部重放/amend 的 author 与原始对象逐项对照，committer 核对本人；原始作者未变不代表本次消息和内容已获批准。不自动重写外部提交来套用个人消息格式；需改消息时作为明确改写内容提交审核。

## 推送

- 需要明确推送授权和 remote/目标完整 ref/源 SHA。用户已经要求提交并推送到明确目标的，不重复询问同一许可；commit 批准本身不包含 push。新远端分支必须有创建意图。
- 查询并获取目标当前 tip，列出到固定源 SHA 的新增范围，确认没有未授权提交且为快进。新分支确认基线、继承历史来源及本次新增范围；不把全部祖先逐条重新要求为本人身份或重新格式化。
- 对本次创作/改写的提交核对已有批准及身份/消息结果；继承历史保留真实作者。发现来源不明、未授权内容或伪造归属，报告具体提交并停止，不用 squash 隐藏。
- 推送前核对远端未变化，只推授权 SHA 到指定 ref，不附带 tags；不默认 --all/--mirror/--force。远端变化重新判断范围，失败不自动升级强推。用户明确要求改写已推送历史时，先明确影响与目标 tip，再使用带精确预期 tip 的保护方式，不能无限重试覆盖新变化。
- 推送后确认目标 tip 和结果。报告区分已准备、已提交、已推送；发布、关闭和清理分别按对应流程处理。

工作流库的日常 JSON/Markdown 保存不等于 Git 提交。本项目 Git 适配脚本不自动 commit/push；meta 是否由 RumSDLC 后台同步由 enable/disable 控制。用户启用 meta 同步后，后台检查点沿用该授权；它不授权代码仓库提交或推送。
