# 使用范围与存储位置

本文件保留设计/实施判据。Topic 的 TASK_CONTEXT、DESIGN 与 Task 正文位于独立工作流库，通过 document 接口定位；产品架构、契约和随代码版本交付的文档继续位于代码仓库 docs/。系统中的 Topic 状态与归属用 API 查询，不从 Markdown 头部读取。设计正文不承担实体元数据修改入口。

# 架构设计、开发方案与冲突检查

本环节把已选需求转为可实施方案，不新增与 Topic 平行的工作对象。判定规则由 agent 执行，记录脚本不证明设计通过、语义无冲突或用户已批准。

## 流程位置

Topic 需要覆盖需求、架构影响、方案、实施准入、验证和交付。Task 按 [tasks.md](tasks.md) 的实际活动滚动组织，可先调查、先复现测试、直接使用已有方案，或在证据变化后回到调查/设计；不把这些职责固定成一组顺序 Task。正式实现对应范围前，仍必须有有效方案并通过实施前检查。

新项目先明确首个可验证目标，再做支撑该目标的初始架构设计；不在尚无目标时凭空设计框架。初始拆分是可调整的，设计发现影响后反馈到规划、依赖、验收和开发线判定，不预先冻结整个里程碑所有实现步骤。

每个开始的 Topic 都按下文 D1—D6 判定方案存放位置；fix、docs 等类型不豁免判定。纯记录/文档主题没有运行架构影响时写明理由、资料范围和验证方式，不强造模块设计。没有产品代码的初始架构 Topic 可以把待验证假设和后续 spike 作为明确交付，而不能声称相关假设已成立。

## 项目级架构触发

| 事件 | 固定动作 |
|---|---|
| 从零启动、尚无可靠基线 | 依据首个目标建立初始架构；已有代码则先核对实际结构，不用理想方案覆盖事实 |
| 新里程碑 | 对照本表的模块、契约、运行和质量约束检查目标；逐项记影响或无影响的依据，只修订受影响部分 |
| 修改模块职责、依赖方向、公共契约、状态所有权或更新模型 | 对受影响部分提出架构调整，列受影响 Topic/模块及迁移路径 |
| 引入/改变联网、存档兼容、回放、并发、平台或性能规模要求 | 复核有关假设、资源预算和验证场景，不能仅按功能清单设计 |
| 实测/原型推翻方案或架构基线明确引用的假设，或跨主题出现不兼容设计 | 标出失效假设和依赖者，修订相关方案与规划 |
| 不改变本表任何架构约束的修复 | 记录核对的约束及无变化依据；方案位置仍按 D1—D6 判定 |

架构基线覆盖首阶段所需的模块职责/依赖、关键数据流与状态所有权、更新时间/线程模型、公共契约、数据持久化及兼容边界、目标环境与质量要求、未知项及验证方法。不强制为尚未提出的联网/回放等未来能力设计完整框架。

性能要求使用真实目标场景、设备/环境、实体或资源规模及测量办法；没有数值时列为待澄清或待测量，不编造预算。区分“已确认约束”“已实现结构”“待验证假设”。

## Topic 开发方案

### 方案位置的固定判定

在 Topic 开始、正式实现前，以及需求/方案/依赖变化或恢复工作时核对 D1—D6。模块以当前架构基线中有职责和边界的模块为准，不把目录数或修改文件数当作模块数；尚无基线且无法确认边界时，该项记“待核实”。

| 编号 | 满足即记“是”的条件 |
|---|---|
| D1 | 新增、删除或改变模块职责、模块间依赖方向、状态所有权、线程/更新模型或跨模块调用流程 |
| D2 | 新增、删除或改变模块间或对外的 API、事件、配置、数据格式的约定行为；按原契约修正内部实现、不改变契约时记“否” |
| D3 | 需要转换已有数据、迁移调用方/配置，或安排新旧实现并存、兼容层、切换/回退步骤；纯代码移动且无上述行为时记“否” |
| D4 | 本 Topic 与其他 Topic 必须协调契约、共同修改方案或安排分阶段切换；仅等待上游按既定契约交付时记“否” |
| D5 | 需要作出下文 A1—A4 任一长期决策，而非仅执行已有 accepted 决策；A 项任一为“是”则本项为“是”，A 项全“否”则为“否”，否则为“待核实” |
| D6 | 用户要求独立方案文档，或已确认的交付物本身就是架构/技术方案 |

- 任一项为“是”：必须使用 Topic 目录下的 DESIGN.md，从 [方案模板](../assets/design.md) 起草；TASK_CONTEXT 只保留判定、摘要和链接。剩余“待核实”项仍需调查，不因已选 DESIGN 就视为已解决。
- 全部为“否”且尚无 DESIGN：方案写在 TASK_CONTEXT 的“架构影响与开发方案”，仍须回答下列七项；没有影响的项写明依据，不以“小改动”略过。已有 DESIGN 时适用下文保留原文件规则。
- 无“是”但有“待核实”：不先判为 TASK_CONTEXT-only；执行已授权且能回答该项的调查，记录问题、证据来源与结果。若缺的是需求、公共契约或架构取舍，向用户提出具体选项及影响。未核实项影响的实现范围不能通过实施前检查，无关范围仍按原有局部准入规则处理。

在 TASK_CONTEXT 记录 `D1—D6：是/否/待核实 + 依据`、方案位置和核对基线；依据须指向需求、契约、代码或已确认决定，不能只写“简单/复杂”。已有结论覆盖相同条件且基线未失效时引用原结论，不重复询问。跨会话次数、讨论轮数、代码行数和主观工作量均不参与分流。

已有 DESIGN.md 的 Topic 后续继续在原文件修订，不因范围缩小把正文搬回 TASK_CONTEXT；从 TASK_CONTEXT 升级时迁移方案正文并留下链接，保留判定记录，不双份维护方案。

方案必须回答：

1. **需求映射**：逐项验收对应什么实现机制、什么证据；不能只有类名和文件清单。
2. **现状与影响**：实际代码基线、相关模块/接口/数据、要保持的行为，引用相关架构约束与决策。
3. **设计**：数据存放与所有权、调用/事件流程、接口、关键错误和边界处理；只有存在真实取舍才比较方案，说明选择与代价。
4. **实施路径**：步骤、依赖、局部结果；方案形成后细化可开始的实现活动。调查、方案形成/修订本身可以提前拥有 Task，不要求先完成方案才允许建立 Task。
5. **兼容和迁移**：旧数据/调用方/在途 Topic 怎么处理；没有影响时给出依据，不填空洞模板。
6. **验证**：按 [verification.md](verification.md) 将验收条件映射到输入/环境、实际检查、通过条件及证据；覆盖运行、测量和整合后复核，人工交互验收明确保留。
7. **未知和冲突**：阻塞项、可接受风险、验证计划和解决去向。

有代码时记录目标分支 SHA（无提交空仓库明确标注）及未提交修改是否影响判断；无代码时记录实际成果/资料基线，不虚构仓库或 SHA。基线是定位依据，不是审批证明。新提交只触及无关区域时无需重做全文；影响相关接口、约束或假设时必须复核。

## Spike 与设计反馈

未知影响技术方向时，先限定问题、实验范围、证据标准和停止条件，再执行已授权的调查/实验。当前 Topic 内查代码现状、验证一个假设或调查故障使用 investigate Task，结论出来即可交接给设计或实现活动；“能独立回答问题”本身不要求新 Topic。研究需要独立的用户验收交付，或服务多个 Topic 而不属于当前 Topic 范围时，按规划规则建立 spike Topic。

初始产品设计未完成不禁止必要原型；原型只验证所声明问题，不自动升级成正式实现。不确定结果要如实记录。得到证据后更新决定、需求拆分、依赖和开发线条件。设计结论可能意味着无需开发线，也可能需要新建开发线；按 lines.md 重新判定，不因前期决定而硬套。

## 冲突检查：四个固定节点

- **近期规划**：比较近期需求的目标、验收语义和关键假设，识别重复、互斥、隐含顺序及总预算风险。
- **方案形成/实施前**：对照架构约束、目标分支事实、依赖 Topic 和影响相同模块/契约的活跃方案。
- **关键变化**：需求追加、调查结论、技术选择改变或依赖更新后，只重新检查影响范围。
- **整合前**：核对最新目标分支和已整合变化，验证实现、方案与当前架构一致。

每次检查至少考虑：需求语义、状态所有权、接口/事件/数据格式、更新顺序与确定性、线程与资源生命周期、兼容迁移、总体性能/内存预算、实施顺序。游戏项目的实际需求决定哪些适用；不要把固定 Tick、确定性或特定物理方案当成所有项目的默认要求。

查找范围从架构概览、本 Topic 影响声明、直接依赖开始；扫描活跃主题元数据/上下文的影响摘要，识别交叉者后才读取其方案。必要时检索代码和接口使用处。不同工作树中已声明的相关在途主题也需纳入；无法读取时明确未覆盖范围，不声称检查完整。不加载全部候选或历史关闭封存正文。

冲突在受影响 Topic 的方案或总上下文记录，不新增全局手工冲突看板。每项写：双方 ID/需求或约束、具体不兼容点、证据、受影响工作、候选处理、决定/待决定者、验证方法和当前是否阻塞。跨 Topic 由一个主记录维护详情，另一侧引用。

需要改动需求优先级、架构方向、公共契约或已确认承诺时，把具体取舍和影响交给用户决定；已有明确决定无需重复请示。普通实现问题在授权范围内解决。无法消除的关键冲突阻塞依赖它的实施，不阻塞无关工作。编译、Git 无冲突或脚本通过不能证明设计相容；用实际场景、针对性测试、预算测量和人工判断补足。

## 实施前检查与失效条件

在 TASK_CONTEXT 的“实施前检查”记录范围、核对基线、结论和证据。结论为“尚未检查 / 通过 / 需复核 / 阻塞”；这是技术准入结论，不是 系统中的 Topic 生命周期状态，不得把 Topic 提前设为 ready（ready 仍表示用户验收后的待整合）。

只有下列条件全部满足，才能实现所检查的范围：
- 目标、范围和验收清楚；实施方案可解释且与当前需求对应。
- 遵守有效架构，或需要的架构调整已有明确决定；阻塞取舍不以默认偏好替代用户决定。
- 影响范围内的阻塞冲突已解决；依赖、实际基线、目标分支与迁移顺序明确。
- 剩余未知项有验证安排，并不妨碍当前实施；需要先实验的部分尚不能直接做正式实现。
- 验证方法明确，用户已授权这项工作。

通过后在授权范围内连续实施，不为每个内部步骤另加审批。局部可开始必须明确可开始与阻塞的边界，不能用局部通过掩盖整个 Topic 尚未解决的问题。出现影响当前方案的需求、架构、契约、基线或证据变化，标为需复核，回到相应设计/检查，不静默换架构。恢复会话也检查记录是否仍有效。

## 文件、版本与关闭封存

### 架构文档按内容职责拆分

不使用项目大小、字数、行数或“过长”作为拆分条件。首次基于真实设计与证据建立文档；没有对应内容就不创建空文件。

| 内容 | 唯一正文位置 |
|---|---|
| 模块职责与边界、模块间依赖和系统级数据流、全局运行/质量/兼容约束、其他架构文档入口 | `docs/architecture/OVERVIEW.md` |
| 单一模块的接口明细、内部数据结构、算法、状态转换和运行细节 | `docs/architecture/<module-slug>.md`；已有该模块正文文件时沿用原路径 |
| 跨模块的接口/事件协议明细、共享数据格式或交互时序明细 | `docs/architecture/contracts/<contract-slug>.md`；已有该契约正文文件时沿用原路径 |
| 本次 Topic 的拟议方案、实施步骤和验证计划 | Topic 的 TASK_CONTEXT 或 DESIGN.md，按 D1—D6 确定 |
| 为什么建立或改变长期约束、候选方案与选择依据 | 下文规定的 `docs/decisions/` 决策记录 |

当架构现状需要记录模块或契约明细时，即建立/更新对应文件，并在 OVERVIEW 增加名称、职责/约束摘要和相对链接；即使明细只有一段，也按此规则放置。只有总览层内容时只保留 OVERVIEW。一段内容同时涉及模块和跨模块契约时，契约定义以 contracts 正文为准，模块文档只写本模块实现并引用契约；总览不复制明细。slug 使用模块/契约已有的小写英文 kebab-case 名称，无名称时根据其职责命名，同一对象不另起同义文件。

已有架构文档在本次需要更新对应内容时按此表整理；未涉及的文档不因长度主动重排。移动已有正文时保留事实和决策历史、修复引用，并随本次文档差异审核。

### 长期决策记录的固定判定

在形成方案、改变方案或已有决定被新证据推翻时逐项核对：

| 编号 | 必须记录的决策 |
|---|---|
| A1 | 建立或改变后续实现必须遵守的模块职责/依赖规则、状态所有权、线程/更新模型，或框架、存储引擎、目标平台的选型约束 |
| A2 | 建立或改变公共契约的版本演进、兼容/迁移政策，或必须持续遵守的性能/资源/确定性要求；按既定政策添加接口或执行迁移不算新政策 |
| A3 | 替代或撤销已有 accepted 决策；不能覆盖旧结论而不保留替代关系 |
| A4 | 用户明确要求将本次选择作为独立、长期可引用的决策记录 |

任一项命中，必须在 `docs/decisions/YYYYMMDD-<slug>.md` 记录背景、选项、结论、代价、适用目标/范围、决定依据、状态（proposed/accepted/superseded）及实现证据。日期取用户时区的实际建档日期，slug 标识该决策。同一尚未定案的决定更新原 proposed 记录；改变已 accepted 结论时新建记录，待新决定获确认后再把旧记录标为 superseded 并互相链接。全部未命中时，选择及理由留在 Topic，不仅因讨论多轮或实现代码多就新增决策文件。

TASK_CONTEXT 保留 `A1—A4：是/否/待核实 + 依据` 及命中的记录链接；事实不足先调查，选择权涉及需求优先级、架构方向、公共契约或已确认承诺时交由用户决定，已有明确决定不重复审批。待决定时保持 proposed，阻塞依赖该决定的实现范围。accepted 必须引用用户已作出的明确决定；accepted 不表示 implemented，实现证据在实际落地后补充。

Topic 的 TASK_CONTEXT/DESIGN 保存当前有效方案、判断与交付入口；调查、推导、实现、测试的过程分别保存在对应 Task，Task 只链接方案正文。历史过程不逐轮累加到 TASK_CONTEXT。记录完成后随 Topic 整体关闭封存，不复制成“当前架构”。

当前架构文档明确区分已实现结构、已确认但未实现的约束/目标和待验证假设；拟议方案主要留在 Topic/决策记录，不能写成现状。代码落地且验证后更新代码仓库相应目标分支的现状说明，整合后再核对。开发线文档说明该线适用范围，不提前声称主干具备；线进入主干时协调目标文档，不能直接接受双方互相冲突的描述。

用户选定的交付物仅为架构方案及设计证据、而不包含对应代码实现时，按规划规则建立 docs Topic；附属于已有实现 Topic 的设计继续留在该 Topic，不因文档数量或篇幅另建 Topic。其研究用 spike，实际结构改造用 refactor/feat 等现有类型，不新增 arch 类型或新流水线实体。架构 Topic 的交付是设计及证据，不能冒充实现完成。所有方案、架构和决策文档的 commit 同样先经用户逐次 review。

非 Git 项目有真实代码时，用实际文件内容基线（例如交付副本或文件校验清单）、测试环境/结果和交付记录定位证据。不得因无 Git 改填 no_code，也不虚构分支或提交 SHA；Git 专用检查仅适用于 Git 项目。
