# 整合、结束与代码清理

Topic 结束前核对当前系统关联与实际代码目标；Mainline/开发线/维护线交付范围分别报告。delivered 和 research-complete 都须用户接受后 ready、实际交付及验证完成；Git 代码交付还须实际整合完成；research-complete 仅限 spike，原型保留/丢弃有明确决定。cancelled/superseded 须用户决定、已有成果与代码处置，替代有不同后继。

Task planned/active/blocked 先解决或真实转出；deferred/cancelled 不能隐藏仍承诺的结果。测试 Task done 可报告失败，必需失败或未知未解决不能视为交付通过。按 verification.md 检查验收映射和最新目标，按 design.md 检查架构/契约/相关主题冲突；实现知识更新到代码仓库相应版本的长期文档。

## 整合方式

默认快进或普通 merge，保留已有提交；已分叉普通 merge，不强制 no-ff。squash 只有以下全部成立时作为明确选项交由用户 review：

1. 本次范围恰好一个 Topic，进入其实际目标，本次后关闭；不是 Line/M/ITER 整体交付或仍继续开发的分支。
2. 列出源端新增提交，每条服务同一行为/契约变更，后续只补齐/修正它；存在可独立接受/回滚的其他行为、依赖、CI、研究或迁移时保留提交，不清楚时也保留。
3. 没有 merge commit 或必须保留外部作者归属的提交。
4. 已核对下游 Topic/分支/工作树，不再依赖这些源提交继续开发，没有保留逐条历史的要求。
5. 最终差异与验收证据齐全，用户明确接受单提交及不保留中间提交的效果；准确消息仍审核。单条提交无需 squash。

独立 Topic 先后整合时，后者核对最新目标影响并验证；依赖未交付上游时按顺序保留历史交付上游，不通过 squash 破坏依赖链。同步目标默认 merge，按真实影响触发，不机械按会话同步。

## 关闭与失败恢复

收尾是 Topic 最后一个活动。完成文档、验证与关闭核对，先结束该 Task，再 topic.close；不为自己的记账递归建 Task。Topic 记录原位 closed，队列移除，历史关联/提交/目标和结果保留，不需要为这些记录在产品主线制造关闭提交。

实际代码交付先检查 Git/内容、审核提交、整合并在目标验证，适配器覆盖完整时再用 closure-plan 检查完整关闭请求、integration-apply 同时带 platform_preview.revision 和 code_revision 重新核对并通过系统接口记录结果。纯摘要纠错可直接走核心平台令牌；若经 Git 适配器，则仍需平台/现场双令牌，只校验目标身份，不要求原代码引用存在。关闭预检不是线上回归，不执行代码操作；目标变化后先复核验证/接受，再刷新预检，不能直接用新令牌掩盖失败。仓库结构不受脚本支持时，必须按 [git-fallback.md](git-fallback.md) 的逐项补证与正常系统预检/写入路径完成，不要求重复运行必然拒绝的脚本，也不得跳过事实核验。业务字段 delivery_record/retention/last_release 引用相应实际结果，Git 提交与保留事实在 extensions.git。git_adapter.py delivery 验证所选整合提交在目标历史、源代码 tip 已包含；获授权 squash 另提供逐项证据。系统只校验引用结构，不读取 Git、不认证用户接受或报告真实性。

Git 项目中的纯调查/报告 Topic、此前从未建立 Topic 代码现场时，按 git-integration.md 的 no_code 路径核对并关闭，delivery_record 指向实际成果；不为满足关闭接口制造空分支或伪造整合 SHA。曾有代码/原型时按其真实处置处理。

代码已整合而工作流写入/同步失败时，保存实际 SHA/结果并重试准确的工作流请求；不重复合并代码、不谎称已共享关闭。系统关闭已完成但存储 Git 尚未提交/推送时，如实报告“本地已关闭，尚未共享”。这些后续手续不重开 Topic。

工作流存储可独立版本管理；其 commit/push 与产品代码提交分开报告，不自动推送。用户未批准新增同步授权时只保存本地。关闭不是发布、push 或清理。

M/ITER/Line 各按自己结果关闭，不连带关闭 Topic。ITER 收尾结果覆盖曾选入项；M 先处理未完成归属；Line 按 lines.md 完成技术退出与证据。

## 清理

只有用户授权后才清理代码分支/工作树。检查已整合事实、保留 ref、未提交/未跟踪/必要忽略文件、依赖、进程与宿主目录归属；实际代码工作树用 git_adapter.py remove 或原宿主管理接口，不递归删除。工具保留分支，不 force/prune/reset/stash。SHA 文本不等于防 GC 的 ref。暂停后移除干净目录可以保留工作流与分支，恢复原 HEAD；不要求为了换目录伪造交付。


## 已关闭事实纠错

发现受管关闭摘要、验证引用或提交等事实错误时，核对真实交付与报告（Git 事实经 closure-plan/integration-apply 重新核对与应用），用 closure.correct 记录原因、已有决定和证据，保留原值。不直接改 JSON，不重开 Topic/Line/M/ITER，不把事实纠错当作新一轮开发。名称仍走 entity.rename，正文纠错注明原因。身份、归属、outcome、关闭日期不在该纠错接口范围；若涉及这些内容，先明确具体修订方案，不能绕过模型约束。旧 ITER 结果不会跟随当前事实纠错自动改写。

通用摘要、证据/验证报告引用的纠错不重新交付代码，也不要求已合法清理的源分支仍存在；直接用系统 closure.correct。涉及代码交付/保留/发布事实或 Git 扩展的实际变化仍按接入手册核验，不把代码变化伪装成摘要修改。


已结束 Task 的结构化 result 事实错误使用 task.correct，Topic/Project 关闭后仍可留痕修正；不经 task.state 重开执行状态，也不把 Task 当作带 entity closure 的对象。实际产品缺陷仍需后续开发活动，记录纠错本身不认证产品结果已修复。

非 Git 项目有真实代码时，用实际文件内容基线（例如交付副本或文件校验清单）、测试环境/结果和交付记录定位证据。不得因无 Git 改填 no_code，也不虚构分支或提交 SHA；Git 专用检查仅适用于 Git 项目。
