# 验证范围与准出

本文件把“适当验证”替换为可检查的选择与结果规则。它用于方案中的验证设计、verify 活动、准备 Topic review 及目标整合后的复核；不增加一个固定 Task 阶段，不要求每次 commit 重跑完整交付测试。

## 确定范围

实现对应范围前，将每条验收条件映射到检查方式、输入/环境、通过条件与证据位置，写在已有 DESIGN/TASK_CONTEXT 或相应 Task。优先引用 Project 的说明字段 中实际可执行命令；没有命令就补充实际命令或明确人工步骤。检查无法执行时记录具体缺失条件，不填“已通过”。

以下按实际改动命中，命中多项取并集：

| 改动 | 必须覆盖 |
|---|---|
| 产品代码或行为 | 受影响目标的构建/类型/静态检查（项目实际配置的门禁），修改行为的正常和边界场景，以及变更直接影响的契约回归 |
| bug 修复 | 原触发输入与预期行为、修复后回归；原失败未能实际复现时明确证据来源和该限制，不能编造修复前失败日志 |
| API/CLI/配置/数据格式 | 受影响调用方或消费者检查，旧输入的兼容/拒绝行为；有迁移时覆盖转换和失败处理，用户操作步骤可执行 |
| 构建/依赖/CI | 对应格式/配置检查和被改变的构建/测试入口；只有解析成功不能证明执行成功，远端专用环境未运行须标未验证 |
| 性能 | 同一输入、规模和环境下的基线/改后测量；采用已确认的指标与阈值，无阈值就只报告观测结果，不声称达标 |
| 界面/交互 | 构建及受影响交互路径的实际运行；需人工体验确认的验收条件保留给用户，截图或构建成功不替代交互验收 |
| 纯文档/记录 | 相关事实与链接/路径核对；含结构字段变化时通过统一接口修改并执行 workflow.py check；不强制无关产品构建 |
| 测试代码/夹具 | 运行改变的测试及其直接依赖用例，确认实际执行而非全跳过；对所验证目标及数据变化如实说明 |

未受影响模块无需无理由全量重跑。判断“不适用”必须给出具体未受影响依据；不能仅写“看起来无关”。项目既有必跑检查仍执行。发现跨模块影响、目标变化或未解释失败时，扩展到能覆盖该影响的检查，不无边界扩大范围。

## 结果、失效与门禁

每项记录实际命令/人工步骤、输入和代码基线、结果（通过/失败/未执行）、证据位置。失败记录诊断与后续去向，未执行记录阻塞及解除条件；测试零执行、全跳过或只生成配置不能记为测试通过。相同基线/输入/环境且影响范围未变的证据可以引用，不重复抄报告。通过依据事先明确的判据：拒绝非法输入、故障复现或否证假设可以预期错误输出/非零退出码并满足判据，必须记录原始结果；不能事后把意外失败改名为预期。研究交付按已约定的问题及结论证据验收，不要求假设一定成立。

- Task done 仍按 tasks.md 判断本次活动是否完成：测试报告可以失败；失败不能被当成交付通过。
- Topic 进入 review：所有当前验收范围的机器检查已执行并通过，必需修复/未知已解决；需要用户执行的人工验收明确列出，等待用户完成。环境阻塞不得改写成不适用；用户真实调整范围时先更新范围及验收映射，再重新判断。
- Topic 进入 ready：在上述基础上，用户接受实际结果，所需人工验收完成。既有环境限制/已知失败不能用一句“风险接受”隐藏仍在范围内的未完成验收。
- 整合后：在实际 target_branch 复核本次验收映射；最终树、输入/环境与已有证据一致的项目可复用。冲突处理、目标新增变化、依赖/配置变化影响的项目必须重跑，目标的必跑门禁必须满足。Line 整合另外覆盖跨成员契约及 LINE_CONTEXT 约定的整体验收，不能仅累加各 Topic 的通过报告。
- 代码、输入、环境或目标变化影响某项结论时，只使相关证据失效；不能确认影响边界时补查或重跑。未跟踪代码/配置参与运行的情况按 git-safety.md 处理，不能把依赖未提交内容的结果宣称为提交自身可通过。

验证与未测范围在提交 review 中报告，但提交本身不等于交付准出。保存未完成成果可使用已获本次批准的 WIP 提交；不得自动推进 Topic 状态。


## 验收记录的位置

验收判据及检查映射在对应实现/验证前明确，不要求开题时生成完整报告。用户要求独立验收文档，或分批/人工验收、多个活动结果需要统一汇总时，用 document 的 acceptance 字段定位 acceptance.md，按 [验收模板](../assets/acceptance.md) 逐步填写。其他情况可在 TASK_CONTEXT 留简明映射和 Task 报告入口。独立正文建立后上下文只保留摘要/链接；判据引用需求主记录，原始执行过程不再抄一遍。

验收文档不赋予业务状态、不自动认证接受。计划先写，真实结果与用户接受后填；无代码成果按实际文稿/成果版本验证。

非 Git 项目有真实代码时，用实际文件内容基线（例如交付副本或文件校验清单）、测试环境/结果和交付记录定位证据。不得因无 Git 改填 no_code，也不虚构分支或提交 SHA；Git 专用检查仅适用于 Git 项目。
