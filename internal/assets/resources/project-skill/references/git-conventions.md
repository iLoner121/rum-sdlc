# 提交身份与消息规范

这是本工作流代码交付的身份与消息规则来源；meta 自动同步检查点按 RumSDLC 同步机制生成。实际创建提交时读取，包括实现、文档、检查点、关闭、merge、squash 和获授权的历史改写。Task 与 commit 不要求一一对应。验证范围按 verification.md，整合策略按 closure.md，批准与实际 Git 操作按 git-safety.md；本文件不重做这些门禁。

## 身份和署名

- 本人本次创作的普通/merge/squash 提交及本人 amend 结果，实际 author 和 committer 的姓名、邮箱均须完全匹配用户已为本仓库确认的身份。以当前对话、本代码仓库的有效 Git 作者配置或本仓库已有明确确认记录为依据；没有确认依据才询问，不从系统登录名或其他仓库推断，不逐次重复询问已确认身份。
- 同时核对 Git 配置和进程环境的有效身份。提交进程显式使用确认的 author/committer；不静默改全局配置、不关闭 hook 或签名。检查脚本必须在与实际提交相同的身份环境下运行。传入脚本的姓名/邮箱必须已经由用户确认，脚本不认证这项确认，也不靠姓名关键词猜测真人；禁止把工具身份填作本人来让检查通过。
- 本人新提交不添加 Co-authored-by、Generated-by、Assisted-by、AI/agent/bot 辅助署名或营销尾注。Signed-off-by 仅在确有项目要求时使用本人真实身份，不自动添加。姓名和邮箱包含产品/公司字符串本身不证明它是 AI 身份。
- 既有外部提交保留真实归属；merge 保留的外部历史无需变成本人。获授权的 cherry-pick/rebase 重放（包括本人旧提交）必须保留原 author，新 committer 为本人，不使用 reset-author 伪装作者。真实合作署名、来源无法确认或归属冲突时由用户决定，不自动删改历史。
- 正文可正常讨论 Codex、Copilot、AI 等技术；代码围栏内可展示署名字符串。禁止的是本次新增的归属声明，不能全篇关键词匹配后删除真实技术内容。脚本只识别明确字段和独立署名行；其他变体由 agent 按此语义核对。

## 消息格式

```text
<type>[(scope)][!]: <summary>

<需要时写中文正文>

BREAKING CHANGE: <破坏的契约和迁移办法，仅破坏性变化填写>
```

- 首行最多 72 个字符，summary 为 ASCII 英文祈使短句，描述具体变化，无末尾句号。禁止仅写 update、fix bugs、complete task、address feedback。代码标识符可以原样引用；正文中文。
- scope 默认用已有长期模块/领域的英文小写 kebab-case；跨项目且无单一主领域可省略。新模块可以引入新 scope；项目约定也可使用项目标识。优先把 Topic 信息放在 summary、正文或可选尾注，不以字段内容解析实体身份，不单凭类似实体编号的 scope 拒绝合法格式。`wip` 是下述检查点的唯一专用例外。
- 标题与可选正文之间空一行。UTF-8、LF 换行、文件末尾换行。agent 默认拟稿时在常规 type(scope): summary 后附真实 Topic 标识，如 feat(cache): Add timeout handling [T-20261105-aabbccdd]；如果会挤占行为说明或超过 72 字符，把完整 Topic 标识移到 Topic: 尾注。没有 Topic 时不编造编号。首次/整合提交或规划归属变化时，正文或尾注补充真实存在的 Milestone/Iteration；日常提交不重复堆叠完整层级。具体规则见下节。用户或项目已有约定可以替换、减少或取消管理标识；缺失或不同的编号不触发格式校验失败。Topic/Task 与提交 SHA 的正式关联仍显式记录在 meta，消息文字不用于推导或校验绑定。
- 仅当变更破坏已确认的 API、配置、数据/存档格式、CLI 或模块契约的向后兼容性时，首行 `!` 与非空 `BREAKING CHANGE:` 必须同时出现；兼容性未破坏时两者均不出现。判据是：既有合法调用、输入或数据，在新版本中不能继续按原约定使用或得到约定行为，或者使用方必须修改调用/配置、转换数据才能继续使用。删除接口、增加必填参数、拒绝既有合法输入、不兼容数据格式，以及违背原契约的默认行为变化均命中。正文说明被破坏的具体约定、受影响使用方和迁移办法；确无迁移办法时写明该事实与处置决定。
- 新增独立 API、保持旧用法及行为的可选参数/配置、兼容的格式扩展、按原契约修复实现或内部重构，不因触及接口文件就标破坏性。核对依据是变更前后的实际契约、输入和行为，不是文件名或 commit type；无法确定兼容性时先查清受影响约定再定案，不能将未知直接判为兼容。commit_check.py 只检查标记配对，兼容性判定由 agent 依据上述证据核对。
- 简单改动只需标题。bug 修复正文写触发条件与修复后的行为；技术取舍写原因；兼容影响与未验证范围如实说明。详细测试报告放活动记录，不在每条 message 重复日志。
- 检查点固定 `chore(wip): ...`，正文写已完成、未完成、能否运行和未验证部分；它不代表交付准出。`revert` 正文说明撤销原因和被撤销的完整 SHA。代码项目本身要求的业务 issue 链接可以保留，默认的管理标识由 agent 拟稿呈现，工具不自动注入，用户可以覆盖。

| type | 条件 |
|---|---|
| feat | 新可用能力 |
| fix | 修复已有行为；对应回归测试可随修复一起 |
| refactor | 保持可观察行为的结构/实现调整，含纯格式整理 |
| perf | 以性能改善为目的，正文给测量结果或明确尚未测量 |
| test | 只改变测试、测试数据 |
| docs | 文档、注释、研究结论、活动或关闭记录 |
| build | 依赖、编译、打包、本地构建工具 |
| ci | CI 工作流和执行环境 |
| chore | 其他工程维护、原型、检查点、整合 |
| revert | 撤销已有提交 |

分支 type 不决定 commit type；不使用 spike/task/merge 或 M/ITER/T/t 等实体缩写替代常规提交类型。标题仍采用 feat/fix/docs 等 type(scope): summary。实体与缩写映射保持原规范，项目/Topic 信息是默认建议呈现、允许用户覆盖的上下文，不是 Git 类型或绑定依据。代码分支命名与绑定按 git-integration.md。

整合消息描述实际代码与目标分支，默认在正文/尾注列出本次实际相关的 Topic 及已知 M/ITER/Line，避免把无关层级塞进标题；用户可覆盖这一建议。管理关联保存在 meta。关闭工作流不要求在产品仓库制造关闭提交。

## 默认建议与用户覆盖

这是 agent 创建时使用的文字 rules，不是 RumSDLC 的字段约束。优先遵从用户明确选择及项目已有命名约定，否则采用以下初稿：

| 位置 | 默认初稿 |
|---|---|
| 新 Topic 分支 | <type>/<Topic短编号>-<slug>，保留 feat/fix/docs 等常规前缀；默认不把 M/ITER 全部拼进分支名 |
| 日常 commit | type(scope): 行为摘要 [Topic-ID]；完整 ID 影响可读性或长度时放 Topic: 尾注 |
| 首次实现提交、整合提交、规划归属变化后的首条相关提交 | 保留 Topic，并在正文/尾注加上真实已知的 Milestone: M1、Iteration: ITER-001 等当时上下文 |
| 普通后续提交 | 默认保留 Topic，不机械复制每一层规划信息；项目要求每条完整标注时可以采用 |

Topic 是追溯当前工作的直接入口；M/ITER 是可能改变的规划归属。历史消息中的归属只说明提交当时的上下文，不保证当前仍属该阶段/迭代。归属变化不重命名已有分支、不重写已有提交；当前关系查询系统，后续适当位置更新说明即可。没有 Milestone 或 Iteration 时省略相应字段，不填假编号或从分支名猜测。一次提交真实涉及多个 Topic 时如实列出，不为凑一个编号误标归属。

若用户指定分支名为 xxxx，就使用该合法 Git 名称并登记关联；若用户要求省略 Topic/M/ITER，则按其选择拟稿。显式关联的 Topic 与名称/消息里出现的编号可以不同，工具不从文字建立、修改或验证关系；agent 不应主动制造误导，但明确用户选择不被命名规则拒绝。

分支脚本只提供可被 --branch 完全覆盖的默认建议；commit_check 只检查原有消息格式/身份，--topic 只是可选上下文参数，不生成消息、不要求某个编号出现、更不解析 M/ITER/T 绑定。常规 Git 合法性和仓库自身有效 hook 仍适用。

## 轻量工具

```sh
python3 -B <工程>/.agents/skills/rum-project/scripts/commit_check.py preflight --repo <root> --name '<已确认姓名>' --email '<已确认邮箱>' --message <消息文件>
python3 -B <工程>/.agents/skills/rum-project/scripts/commit_check.py postcheck --repo <root> --name '<已确认姓名>' --email '<已确认邮箱>' --message <同一消息文件> --commit <实际提交SHA>
```

工具只读，不 commit/push、不写身份登记/审核快照/审计文件、不扫描全历史、不改 hook。preflight 检查当前有效双重身份和消息格式；postcheck 检查实际提交的双重身份及消息字节与原文件相同，并返回 tree/parents 供 agent 核对。脚本先检查仓库覆盖，不支持时必须按 git-fallback.md 的具体证据要求处理。成功退出 0，校验失败退出 1，参数错误退出 2。

自动检查类型、首行长度/基本英文字符、scope 格式、破坏性标记配对和明确署名。agent 核对祈使表达、scope 含义、是否真的破坏兼容、正文信息、WIP/revert 内容、用户批准、提交树和父提交；脚本成功不证明这些语义成立。

工具用于本人创作的提交，包括本人新建的 merge/squash/amend。保留原 author 的重放及外部 amend 不使用“本人双重身份相等”模式，按 git-safety.md 的逐项原始作者对照执行；不为通过脚本改写真实作者。旧 personal-git-delivery 不再是本工作流的运行依赖，也不调用其 review_guard.py。

既有提交和代码项目原有业务引用不因新规则被重写。纯格式检查不覆盖的项目规范，由 agent 按仓库约束核对，不通过改作者、删来源或绕过 hook 迎合脚本。
