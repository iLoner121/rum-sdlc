# 脚本覆盖不足时的执行规则

在脚本返回失败、unknown、checks_complete=false，或遇到子模块、LFS/自定义过滤器、浅/部分克隆、稀疏检出、替换历史、特殊远端、无法访问的工作树时读取本页。脚本成功也只证明输出列出的检查，不认证授权、测试或交付。RumSDLC doctor 正常、远端 PR 已合并、工作流 ready 均不授权推送。

## 不完整不是通过

暂停受影响的提交、合并、推送或清理，保留代码、分支、未跟踪/忽略文件和部分成功结果；调查、设计及无关工作可继续。不自动把 Topic 改为 blocked，不反复重跑不支持的命令，不使用 no_code、假 SHA、空字符串、手改索引或删除缓存绕过检查。

先辨别是实际检查失败、环境暂不可用，还是工具不支持。环境故障只在查清原因后有界重试；工具不支持则使用仓库既有工具、Git 标准命令或托管平台的明确接口补证。沿用已有有效授权，不因换工具重复索取授权；若拟执行动作或影响扩大，先说明具体变化。

## 替代检查必须回答的事实

| 活动 | 必须补齐的事实 |
|---|---|
| 提交 | 当前仓库/工作树准确；暂存树、父提交、完整消息与已审阅结果相同；作者/提交者适用规则正确；冲突已解决；验证针对实际提交内容；hook/签名保持 |
| 合并与交付 | 明确源提交和目标分支/提交；源内容如何进入目标；squash/rebase 不能仅用祖先关系判断；在实际目标上复核测试与验收；已合并不证明之后未撤销 |
| 推送 | 实际 fetch/push URL、目标完整 ref、固定源 SHA；新分支的基线与创建意图，或现有目标的最新远端 SHA；逐条核对全部待发提交及净差异、来源/归属、测试、授权范围；不得夹带其他工作 |
| 工作树移除 | 所有工作树注册与占用、进程/端口/数据资源、tracked/untracked/ignored 内容、子模块内容；HEAD 有真实保留 ref；目标准确且已获清理授权 |
| 流程记录 | 实际事实和限制写入 meta 的 Task/交付记录，再经系统预检与提交；不能把工具成功或一段“已检查”文字伪装成真实证据 |

每一项写清使用的方法、精确对象、结果、证据位置和未覆盖项。不能用一句“人工等价检查”替代；关键事实仍未知就保留现场并报告具体阻塞，不执行该代码动作。

## 补证后的流程写入路径

某仓库结构长期不在脚本覆盖范围内时，不能在补齐证据后又强制重跑必然拒绝的 closure-plan/integration-apply。这里使用正常的系统接口，绝不增加 skip-check、force 或伪造脚本通过结果：

1. 按上表逐项取得真实证据，并将精确仓库、源/目标 SHA、实际指针/内容基线、核验命令或 API、结果和限制写入当前 Task/交付文档。只有全部与本次动作相关的必要事实确认、测试满足、用户接受适用时，才继续。
2. 需要 Git Line 配置时，使用标准 Git 解析实际分支和 base_commit，再按 api.md 用 extension.set 登记。准备/验证目标变更时分别构造 topic.integration.prepare 或 relation.move 的完整请求；恢复 review 时使用 topic.state（status=review、verification 和 integration_proof），保留 api.md 要求的生命周期、旧 HEAD 保留、依赖/契约及真实验证证据。不能仅凭业务状态推测代码事实。
3. 关闭前按 closure.md 检查 Task、验收和实际交付。Git 的 integration_commit 必须真实且已按原始/普通合并、或获准 squash 的相应方法核验；retained_ref 必须真实可达。其他接入可以使用描述实际内容基线的业务证据，不伪装成 Git/no_code。通用摘要纠错直接走 closure.correct，不重新要求代码交付。
4. 用工程脚本 workflow.py command --store <meta> --request <仓库外请求JSON> --dry-run，审核返回的请求效果和 revision；紧邻写入复核相关代码事实没有改变，再对同一请求使用 --expect-revision <令牌>。或者调用等价的 rum platform command API。请求文件和补证记录均在代码仓库之外。
5. 系统只校验数据与并发，不能认证这份补证。报告明确区分“脚本覆盖不足、agent 已用哪些具体方式补齐、系统记录已写入”。任何必要事实仍未知时，留在调查/验证状态，不进入 ready/关闭或推送。

这条路径保留已有合法授权，但不扩大授权、不改变验收条件、不代替实际 Git 操作。代码已整合而记录失败时仅重试准确的流程写入，不重复合并；预检令牌或外部事实变化时重新核对受影响内容。

## 常见仓库差异

- 子模块：列出每个层级的提交指针、初始化情况、脏/未跟踪内容及远端可达性。分别在实际子仓库核验，先确保引用的子模块提交可获得，再处理父仓库。父仓库干净不证明子模块干净；未初始化也不等于没有改动。
- LFS/过滤器：核对项目属性、指针和实际内容、对象可获得性及所需工具。只读脚本会抑制过滤器并报告不完整；不能以抑制后的 diff 宣称语义一致。真实代码操作保留项目过滤器和 hooks。
- 浅/部分克隆、稀疏检出、assume-unchanged/skip-worktree：明确哪些历史或内容缺失/隐藏，按授权用标准工具补齐，或取得确实覆盖相关对象的远端证据。不要把本地找不到解释为远端没有。
- 多 push URL、URL rewrite、镜像、非标准 refspec：明确实际每个写入目标。普通脚本不放行；必要时使用已确认的具体地址和 ref，仍遵守原授权，禁止隐含 --all、--mirror、tags 或强推。
- 不认识的仓库/托管服务：先查项目文档和可用 CLI/API；公司内部优先 bytedcli。浏览器/鼠标沿用用户当前会话约束，不能作为自动回退。

## 推送前后

repo_check push-plan 只提供待审核范围，不执行或批准推送。即使其返回 ok=true，也必须核对上述内容；本地脏内容如用于测试，要说明与固定源 SHA 的区别。新远端分支目前走本页的明确基线/范围核验，不跳过。

准备完成后，沿用/取得对实际范围有效的授权，紧邻推送重查远端目标。变化则重新判断和更新受影响的审核；推送固定源 SHA 到一个明确完整 ref，不用移动中的 HEAD、不强推、不附带未授权分支或标签。正常 push 仍由 Git 拒绝非快进；失败不升级为 force。推送后读取远端实际 tip，区分“已准备、已提交、已推送、已验收”，失败保留恢复依据。

## 管理数据不得进入代码仓库

工具记录放设备的 agent-state/git 目录；审批材料、消息临时文件和检查缓存放代码树与 Git 元数据之外。共享关联、活动和证据放 meta。不得生成代码仓库内的 RumSDLC 索引、日志、管理文档、专用 Git hook/include，agent 拟稿默认建议呈现真实 Topic，首次/整合/规划变化时补充 M/ITER；这些建议可由用户或项目约定覆盖，工具不强制注入。分支用 feat/fix/docs 等常规前缀的默认建议，允许自定义，不强制名称里的 Topic 编号匹配关联。项目原有开发文档与有效开发约束继续保留。
