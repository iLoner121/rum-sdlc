# Task：一次活动的执行记录

Topic 承担一个开发主题的完整流程与最终交付；Task 承担其中一件事及其结果，同时隔离这件事的过程上下文。调查得到结论、设计形成方案、实现产生代码、测试形成报告，都可以完成一个 Task；不要求一个 Task 包含从调研到交付的全流程，也不要求其结果能独立发布。

Task 不另建分支，不设置 review/ready/closed，不单独归档。Task done 不表示功能正确、测试通过、方案获批或 Topic 已验收。用户审批需求/架构取舍、具体 Git 提交和 Topic 最终交付，不为每次普通 Task 切换新增审批。

## 活动类型与结束产物

新 Task 的 Kind 标注本次主要活动。下表用于识别活动，不是流程阶段清单；不要求五类齐全、不规定顺序、不限制同类出现次数。

| Kind | 本次活动 | 可用于结束本次活动的产物 |
|---|---|---|
| investigate | 查明一个代码现状、行为、原因或可行性问题 | 问题的回答及证据；达到预定停止条件仍不能确定时，给出已知、未知和下一步 |
| design | 为明确范围形成或修订技术方案 | 对应范围的方案、取舍和待确认事项；“方案已产出”与“用户已批准”分别记录 |
| implement | 按当前有效方案编写或修改一个明确范围的实现 | 代码/配置/测试代码等变更、实际完成内容和未验证范围；不自动承诺后续测试已通过 |
| verify | 执行一组明确的测试、复现、检查或测量 | 实际范围、环境、结果和证据，结果可以通过、失败或带明确限制；失败发现移交后续处理 |
| process | 完成具体的整合、文档同步、资料整理或交接操作 | 实际操作结果及可核查记录；commit/push/清理仍遵守各自授权 |

不能归入上述类型时可使用表达实际活动的小写英文 kebab-case Kind，并在“本次活动与结束条件”说明其含义；不为类型增加生命周期、强制步骤或额外审批。类型不会赋予操作授权，不得把实现改称 process 以绕过设计门禁。

## 按活动滚动组织工作

进入 Topic 后，agent 采用工程根目录 AGENTS.md 与项目共享 skill，再读取用户指向的需求/文档、系统中的 Topic/关系查询结果、TASK_CONTEXT 及当前活动的必要输入；然后按以下规则推进，而非要求用户逐个创建 Task：

1. 明确当前已获授权的目标、现有事实、阻塞和下一件要做的事。已有 Task 正在做同一件事则恢复；否则在开始实质活动前新建 Task，写目标、输入、预期产物和结束条件，再转 active。
2. 信息不足以选择方案时，以调查活动解决具体未知；已有充分证据时直接进入设计或实现，不补做无意义的调查。进入新活动前只计划已能说明目的和输入的后续 Task，不预先铺满整个 Topic。
3. 执行过程中将方法、发现、尝试与日志引用留在当前 Task/附件。问题或产物改变到需要另一件事时，先记录当前结果/阻塞及交接，再创建或恢复下一 Task；不能持续向一个 Task 追加调查、设计、实现、测试等不同目的的全过程。
4. 本次结束条件达到后，保存产物、结论、限制与后续问题，标记 done；将最小交接摘要和链接回写 TASK_CONTEXT。依据结果及原授权，自主选择下一活动。用户授权“把这个 Topic 做完”允许持续推进其内部活动，但不授权下一 Topic，也不替代 Git 逐次 review。
5. 用户要求“先出方案给我审核”时，设计 Task 在方案形成、校核并提交审阅后可以 done，但方案继续标为待审核；依赖审核的实现不得开始。已有明确批准不重复询问。仅请求调查/设计时不能推断实现已获授权。
6. 测试发现失败后可以结束该测试 Task，另开调查/修复/复测 Task，保留原测试记录。新证据推翻方案则回到调查或设计活动；实现前检查失效的范围先复核。活动可以循环、跳过已满足的环节或按实际依赖交错，不强制“调查→设计→实现→测试”。

“写入本 Task 状态”“更新索引”“给用户报告本次结果”等是当前活动的记账动作，不为它们递归创建 Task。一次命令、一个文件、一次对话或一次 commit 也不自动形成 Task。

## 何时拆开、何时继续

- **拆开**：当前问题已回答，需要回答新问题；方案产出后要开始实现；代码产出后要进行一组独立测试；测试发现需另行诊断/修复；用户要求一份独立可交接产物。每一件事有自己的目标、输入、结束条件，前后通过引用交接。
- **继续当前 Task**：仍在回答同一个问题、实现同一范围或执行同一组测试；短暂查调用方、编译检查、修复本次操作笔误等仅服务当前活动。不能把每个辅助动作拆成碎片，也不能以“还是同一个功能”为由把不同活动合并。
- **多轮调查**：为本次调查补齐直接证据仍属原 Task；一轮调查已有结论（含明确的未知及限制），下一轮要验证新假设、进入新的证据范围或执行独立实验时，记录交接后另建，即使仍服务同一个 Topic 问题。尚未达到本次停止条件却被其他活动阻挡时保留 blocked，不为切换而伪装 done。
- **实现粒度**：一次 implement Task 对应一个明确的代码修改目标及其方案范围。不同修改目标有不同输入/依赖，或能分别确认代码产物时拆开；同一目标涉及多个文件可放一起。不要求每个实现 Task 自带完整调研、设计和测试活动。编写回归测试代码可属于实现产物，专门运行和分析测试结果可为 verify。
- **Topic 粒度**：出现新的用户目标、独立验收边界或需要另行安排交付的范围时，回到 Topic 规划；只是活动多或类型改变，不自动拆 Topic。

技术预研与方案形成按问题区分：查明“能否做/现在怎样/为什么失败”是 investigate；决定“具体怎样做”是 design。若只为当前方案核对一个已有接口且无需独立结论，留在设计 Task；需要实验回答且结果影响技术方向时，先独立 investigate。影响多个 Topic 或需要独立验收交付的研究，才按规划规则建立 spike Topic，普通代码现状调查不自动升级为 spike Topic。

## 数量只触发诊断

不规定每个 Topic 必须多少 Task，不强凑两项或四项，不按类型凑齐步骤。

- **低数量检查**：准备 Topic review 时，累计只有 0—2 个 Task，检查是否把调查/设计/实现/测试混写在一个 Task 或 TASK_CONTEXT，是否遗漏实际发生的活动，以及 Topic 本身是否确实只需一两件事。留下结论；实际简单可保留。刚启动时只有一个调查 Task 属于正常滚动规划，不触发低数量警报。
- **高数量检查**：累计创建第 13 个 Task 起，在开始新增活动前检查 Topic 范围、重复调查/返工、方案有效性与过细拆分。每批因同一原因新增的 Task 合并复核一次；已复核的同一批不反复提示，但因新问题再次增加时重新检查。
- 数量是此 Topic 全部已创建 Task ID 的累计数，包含 done/deferred/cancelled，不删除历史以降低计数。正常的“测试发现问题→调查→修复→复测”计为不同活动；不能为了避开预警把它们并入旧 Task。
- 诊断在 TASK_CONTEXT 保留问题、依据、处理和当前结论。授权范围内的活动调整由 agent 执行；改变 Topic 目标/验收/已确认承诺时交给用户决定。超过阈值不自动禁止继续、不自动拆 Topic；数量不是完成标准。

## 上下文分层与交接

- **TASK_CONTEXT**：只保留 Topic 目标/验收、当前有效方案摘要与链接、实施前结论、Task 索引（ID/类型/标题/链接）、当前 Task 指针及下一步、阻塞和有效决定、交付证据摘要。完成一个 Task 后更新“现在已知什么、接下来做什么”，不逐轮累加聊天记录；原始过程留在 Task。
- **Task 文件**：保存这次活动的目标/结束条件、输入引用、过程与产物、结论与交接；长日志放 Topic artifacts 并引用。无需填满不适用的过程模板，也不复制整份需求或前置 Task 正文。
- **设计正文**：仍按 design.md 的 D1—D6 放在 TASK_CONTEXT 的方案区或 DESIGN.md；设计 Task 保存调查/推导、修改原因和产物链接。TASK_CONTEXT 只保留当前有效的方案内容/引用，旧推导留在 Task，不能把多轮过程搬进方案区。当前方案与历史证据只各维护一份。
- **切换与恢复**：交接摘要必须包含活动结果、证据位置、仍未知/失败的部分、下一活动所需输入。下一 Task 只加载摘要和直接相关证据；需要原始细节才定向读取前置 Task，不默认加载全部 Task 正文。当前 Task 指针只用于定位，不复制其状态，也不意味着获得写权限。
- **已完成活动**：修复、再设计、复测一般建立后续 Task 并引用原记录，保留当时事实。仅在所属 Topic 尚未关闭，且发现原 Task 被错误标记为完成（原结束条件实际未达到或完成依据存在事实错误）时，才注明原因将同一 Task 从 done 改回 active；后来的代码失败不能自动抹去先前调查/测试已经完成的事实。

## 状态与准入准出

主线为 `planned → active → done`；blocked、deferred、cancelled 表达例外。新 Task 初始 planned，状态只保存在系统 tasks 表。

| 状态 | 含义与进入条件 | 允许的后续状态 |
|---|---|---|
| planned | 已登记，尚未执行；开始前填明本次活动、输入、预期产物及结束条件 | active、blocked、deferred、cancelled |
| active | 所需输入可用、活动在授权范围内；实现对应的方案/准入已有效，调查有问题和停止条件 | done、blocked、deferred、cancelled |
| done | 本次活动已按结束条件执行，实际产物/结论/证据与后续去向已记录；结果可以暴露失败，不代表 Topic 可交付 | active，仅限所属 Topic 尚未关闭时纠正错误的完成状态 |
| blocked | 活动仍需完成，但缺输入、依赖、环境或决定；明确障碍与解除条件 | planned、active、deferred、cancelled；恢复需记录解除依据 |
| deferred | 暂不继续这次活动；明确原因及恢复条件或后继位置 | planned、cancelled；重新选入先核对输入和结束条件 |
| cancelled | 已决定不再执行本活动；说明原因、已有资料/代码处置及替代者 | 无；后续新活动另建 Task |

未列出的转换不允许。blocked 恢复后立即执行才转 active，否则回 planned；deferred 回 planned 不代表获得新范围授权。临时停下或 Topic 暂停时保留 Task 实际状态和恢复入口，不增加 Task paused 状态；真正缺输入才标 blocked。

### done 的固定判据

以下全部成立才可 done：本次事先明确的活动/停止条件已达到；产物与证据可定位；结论明确区分已完成/失败/未知/未验证；仍需处理的事项已交接，未把 Topic 的必需工作藏掉。

- 调查完成：有问题的回答或达到预定停止条件的“不确定”结论及证据；不强制在同一 Task 决定并实现方案。
- 设计完成：对应范围的方案已形成并完成本次约定的校核，待批准事项已列出；不以“用户还未批准”为由把设计与后续实施合在一起。
- 实现完成：约定代码产物已形成并自查修改范围、已知遗漏和可定位性，记录实际做过的构建/检查及未验证部分；后续独立测试不必塞入本 Task。若本 Task 明确约定某项检查为结束条件，则不能未做便标 done。
- 测试完成：约定检查实际执行完毕并形成可解释报告；发现失败仍可 done，但失败必须进入交接与 Topic 未解决项。因环境缺失尚未执行约定检查时为 blocked；若调查运行障碍本身就是另一次活动，其结论可单独完成。
- 流程处理完成：约定操作实际发生并有记录；只准备未执行时不能宣称操作完成。没有已获授权的 commit/push/清理，不得用 Task done 冒充完成。

活动结束条件不能事后降低以掩盖未执行工作；真正改变活动目的时保留原记录、说明取消/延期/范围决定，再登记后续活动。类型不代替这些判据。

## 与 Topic 生命周期的衔接

Topic 为 active 且所属 Line（如有）为 active 时执行各类已授权活动。Line 为 integrating 时仅允许已有 review/ready 成员的 verify/process 与关闭；允许记录成员 paused/blocked，恢复必须先将 Line 退回 active，再按 Topic 门禁恢复 active，具体顺序见 lines.md。新增成员或调查/设计/实现先将 Line 退回 active。Line paused 时不开始或完成实质活动，成员状态不随 Line 自动变化。review/ready 阶段可以创建、执行 verify/process Task，分别支撑人工验收准备、整合后验证、文档同步或交接；不能借此继续未获验收的实现。发现需要代码、方案或验收范围变化时，先将 Topic 退回 active 并使相关旧结论失效，再开始对应活动。其他自定义类型、未标类型的旧 Task 仅在 active Topic 执行，避免靠名称推断阶段权限。

| Topic 转换 | 必须满足的条件 |
|---|---|
| planned → active | 目标、授权范围和实际基线已核对；活动可先是调查/方案，未通过实施前检查不得直接正式实现 |
| active → review | Topic 交付物已准备，逐项验收映射和实际自检证据齐全；无 planned/active/blocked Task；所有 Task 暴露的必需修复/未知已有解决证据；延期/取消不隐藏承诺。待用户人工验收单独列出 |
| review → ready | 用户明确接受具体结果，所需人工验收完成；无 planned/active/blocked Task 或仍待修复的交付失败，转出活动不隐藏承诺。Task 全 done 和方案获批均不能替代最终验收 |
| review/ready → active | 用户要求修改，或新证据使方案/实现/交付结论失效；记录原因及影响，创建后续活动或按事实纠错规则重开 Task |
| ready → closed | 满足 closure.md 的目标整合、整合后验证及记录条件；所有 Task 已结束或明确转出，交付失败已解决；实际产品代码提交/整合遵守 Git review，工作流关闭通过系统接口记录 |

verify Task 的 done 只表示测试活动完成；若报告失败，即使所有 Task 都 done，agent 仍不得将 Topic 推进 review/ready/交付关闭。必须先处理该失败或由用户明确调整其所属验收范围并留下依据。

取消/替代 Topic 由用户决定，未完成 Task 逐项取消/转出，不伪造 done。收尾 Task 是最后一个活动；按 [closure.md](closure.md) 完成文档整理、关闭记录和关闭核对后，先记录该 Task 完成，再将 Topic 标记为 closed，两项记账属于同一次收尾。之后的工作流存储提交/推送、共享状态核对及获授权的 Git 清理不另建 Task，也不重开 Topic。Task 自身记账不另起 Task。

## 系统操作与正文

名称、Kind、状态、所属 Topic 和活动结果引用由 task.create/task.kind/task.state 及 task.correct 接口维护；Task 正文是自由 Markdown，不再解析正文的 Status/Topic/Kind。定位使用 document 接口；Topic 的 TASK_CONTEXT 保持索引、当前活动指针、有效结论和下一步。状态和类型动态查询，不复制可编辑台账。

完整接口与参数见 [api.md](api.md)。新活动默认 planned；先填写问题、产物和停止条件，再 active。done 的 result 可指向报告，报告允许失败但不能用于交付通过。deferred 必须 destination，异常原因在请求 reason。历史未标类型不猜测，继续前使用 task.kind。

数量诊断由 task-summary 返回，既有 0—2 / >12 的判据和非配额语义保持。关系变更和新基线复核按 planning.md/lines.md；改变交付 Line 不搬代码、不覆盖旧测试，新的适配和复测另建活动。系统接口没有代码分支权限门禁；实际代码现场的单写入者与授权在 Git 集成层处理。


## 结束后发现事实记录错误

同一次已结束活动的结果写错、证据引用写错或报告结论有事实错误时，使用 task.correct 留痕修正 result，写清原因、实际证据和已有纠错授权。Topic/Project 已关闭也可纠错；不把它们重开，不改变 Task 的 done，也不假装重新执行活动。原值保留在系统历史，当前查询显示修正值，正文中的相关说明按需协调。

若原活动其实没有执行完，Topic 尚开放时按既有 done→active 门禁处理；若要开展新的修复/复测，则建立相应活动。纠错不能把真实失败改写为成功、降低原结束条件或代替新验证。已关闭 Topic 暴露产品问题时如实纠正记录，再按新需求/新 Topic 处理后续工作；不以纠错绕过开发与验收。
