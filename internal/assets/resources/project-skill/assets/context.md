# Topic 上下文

身份、类型和生命周期状态以系统实体查询为准，M、工作集合、Line 与整合目标以关系解析为准。实际代码分支从 Git 集成层的本地绑定查询；不在这里维护另一份归属或状态列表。

## 执行规则与文档入口

采用的配置来源、profile_id/revision、采用日期与资源摘要；AGENTS.md 的接管读取情况。按需链接 PRD.md、DESIGN.md、acceptance.md；未独立建文档时说明正文所在位置，不把“尚未需要”记成已完成。

## 目标与范围

根据真实需求填写；已有 PRD/权威需求时只留范围摘要与链接。纯调查/文档写清交付物，不冒充实现完成。

## 验收条件

列出可观察的结束条件或引用 PRD 中的稳定判据；spike 使用待回答问题及证据标准。验收记录独立后只留摘要/链接，实际结果与用户接受在真实发生后填写。

## 架构影响与开发方案

影响模块、接口、数据、相关 Topic；引用实际架构/决策与核对基线。读取本 Topic 的 workflow/references/design.md，记录 D1—D6 / A1—A4 各项的“是/否/待核实”及证据、方案位置和决策链接。任一 D 项命中使用 DESIGN.md，此处只留摘要和链接；全部未命中且尚无 DESIGN 时在此写方案，覆盖规范的七项内容。待核实项写清调查或待用户决定的事项，不把未知判为无影响。纯文档无运行架构影响时写明理由。

## 实施前检查

初始结论：尚未检查。

实施前记录检查范围、目标基线及相关未提交变化、验收映射、架构相容性、冲突/未知项处理、依赖与验证安排。结论只能基于证据填写为通过、需复核或阻塞；不改变 系统中 ready 的验收语义。

## 计划与 Task 索引

按本 Topic 的 workflow/references/tasks.md，以一次调查、设计、实现、测试或流程处理为活动建立 Task；根据新证据逐步确定下一件事，不预先凑齐阶段。索引只写 ID、类型、标题、链接，不复制正文或状态表。调查和方案形成本身可先有 Task；实现活动在对应方案/准入有效后开始。

准备交付时仅 0—2 个 Task 才复核是否混写/遗漏活动；累计第 13 个起在新增活动开始前诊断范围、返工或过细拆分。数量只触发复核，记录诊断及处理，不强凑任务、不因数量自动拆 Topic。

## 关键决策、冲突与范围变化

保留影响后续判断的结论及原因；冲突详情放在方案正文或相关调查 Task，只维护一处并引用。需求、架构、契约、基线或证据变化影响当前方案时，原实施前检查失效，重新核对 D/A 判定并回到相关设计复核。

## 当前进展与恢复入口

保留当前 Task ID/链接、当前有效结论、阻塞/未验证事项和下一活动所需输入。每次活动交接后更新“现在怎样、接下来做什么”，不逐轮追加调查或试错过程。过程与长日志留在 Task/附件；恢复时只加载当前活动与直接相关证据，并核对设计基线是否仍有效。

## 验证与交付结论

写 Topic 交付与验收映射、验证结果摘要和证据链接、方案偏差、知识文档更新及遗留事项去向，不复制各 Task 全文。测试 Task done 只代表测试活动结束；失败/未知必须记录解决去向，未解决的必需结果阻挡 Topic 交付。未运行的验证明确标注，进入开发线不等于进入主干。

## 归属调整与基线验证

发生调整时引用 系统历史中的对应事件，说明当前目标、未完成活动的输入变化和验证报告入口；不复制完整变更历史。迁移后旧基线测试不作为新目标的通过证据。
